# i18n (internationalization)

Internationalization here is **[`next-intl`](https://next-intl.dev)** on the App
Router — **not** a Next.js feature. The Pages Router's built-in `i18n` config
block was dropped in the App Router; Next.js now provides only the generic
primitives (the proxy runtime, the `[locale]` dynamic segment, `redirect`/
`rewrite`), and `next-intl` supplies the locale logic on top.

Supported locales: **`en` (default), `fr`, `es`**.

## The moving parts

| File | Role |
|---|---|
| [`src/i18n/routing.ts`](../../src/i18n/routing.ts) | Single source of truth: the locale list, `defaultLocale`, and `localePrefix`. Every other piece reads from here. |
| [`src/proxy.ts`](../../src/proxy.ts) | Runs `createMiddleware(routing)` before routing — negotiates the locale and redirects/rewrites the URL. See [proxy.ts docs](./proxy.md). |
| [`src/app/[locale]/layout.tsx`](../../src/app/[locale]/layout.tsx) | Consumes the resolved locale: guards it, calls `setRequestLocale`, sets `<html lang>`, mounts `NextIntlClientProvider`. |
| [`src/i18n/request.ts`](../../src/i18n/request.ts) | Per-request config: resolves the active locale and loads its message JSON. |
| [`src/i18n/navigation.ts`](../../src/i18n/navigation.ts) | Locale-aware `Link`, `redirect`, `usePathname`, `useRouter`, `getPathname`. |
| [`messages/<locale>.json`](../../messages/) | The translation dictionaries (`en.json`, `fr.json`, `es.json`). |
| [`src/components/LocaleSwitcher.tsx`](../../src/components/LocaleSwitcher.tsx) | The language `<select>`; switches locale via the navigation `useRouter`. |

## How a request resolves its locale

```
URL  ──▶  src/proxy.ts             negotiate + rewrite/redirect  (sets X-NEXT-INTL-LOCALE header)
     ──▶  src/app/[locale]/layout  read params.locale → setRequestLocale(locale)
     ──▶  src/i18n/request.ts      load messages/<locale>.json
     ──▶  components               useTranslations() / getTranslations()
```

The proxy decides *which* locale you're on; the layout renders *given* that
decision. See [proxy.ts docs](./proxy.md) for negotiation order (cookie →
`Accept-Language` → default) and the rewrite mechanics.

### Micro level

The layout does `const { locale } = await params` (the `[locale]` segment value)
and calls `setRequestLocale(locale)`, which writes it into a single per-request
slot. `request.ts` reads that slot back via `getRequestLocale()` (falling back to
the `X-NEXT-INTL-LOCALE` header) to load the messages — one slot means **one
locale per request**.

## Why `/en` never appears in the URL

`localePrefix: "as-needed"` in [`routing.ts`](../../src/i18n/routing.ts): the
default locale gets **no** prefix, the others do.

| URL | Locale |
|---|---|
| `/dashboard` | `en` (default, rewritten to `/en/dashboard` internally) |
| `/fr/dashboard` | `fr` |
| `/es/dashboard` | `es` |

The browser URL stays `/dashboard`; the `[locale]` segment still receives `en`
inside the app. The `[locale]` folder name is **convention**, not a `next-intl`
keyword — the binding happens in the layout via `setRequestLocale(locale)`.

## Reading translations

**Server Components** (default) — `getTranslations` is async:

```tsx
import { getTranslations } from "next-intl/server";

const t = await getTranslations("Dashboard");
return <h1>{t("title")}</h1>;
```

**Client Components** (`'use client'`) — `useTranslations`, backed by
`NextIntlClientProvider` in the layout:

```tsx
import { useTranslations } from "next-intl";

const t = useTranslations("Login");
return <button>{t("submit.idle")}</button>;
```

The argument (`"Dashboard"`, `"Login"`) is the top-level namespace in the message
JSON; nested keys use dot paths (`t("submit.idle")`). Interpolation uses
`{name}` placeholders: `t("success", { email })`.

## Navigation must go through `src/i18n/navigation.ts`

Because `en` has no prefix but `fr`/`es` do, raw `next/link` / `next/navigation`
can't keep the prefix correct. Always import from
[`@/i18n/navigation`](../../src/i18n/navigation.ts):

```tsx
import { Link, useRouter } from "@/i18n/navigation";

<Link href="/dashboard">…</Link>          // → /dashboard on en, /fr/dashboard on fr
router.replace(pathname, { locale });      // switch locale, keep the path
```

## Adding a locale

1. Add the code to `locales` in [`routing.ts`](../../src/i18n/routing.ts) (e.g. `"de"`).
2. Create `messages/de.json` with the same key structure as `en.json`.
3. Add its display name under `LocaleSwitcher.locales` in **every** message file.

`generateStaticParams` in the layout and `LocaleSwitcher` both read
`routing.locales`, so they pick up the new locale automatically.

## Adding a translated string

1. Add the key to `messages/en.json` under the right namespace.
2. Mirror it in `fr.json` and `es.json` (keys must match across all files).
3. Read it with `t("yourKey")` from the matching namespace.
